# Schlange verification map

This directory is the maintained source for verifying what Schlange does, feature by feature.
Read this index before driving the binary, then use the matching feature file as the recipe.
Launch, doctor, evidence and cleanup are in [`../SKILL.md`](../SKILL.md).

## Baseline preconditions

- The release binary of this checkout is built: `.agents/skills/verify-schlange/scripts/verify.sh launch`.
- `target/release/schlange doctor` reports no FAIL and the expected version.
- The pinned Mergify sources are in `.research/mergify/` (`tools/fetch-mergify-sources` exits 0);
  `config validate` needs the schema, `sim run` does not.
- Scenarios run in the simulated forge; GitHub behaviour is tested against the fake GitHub (`crates/schlange-github-fake`), never against github.com.
- With `--image`: the image `schlange:verify` was built by this run; never drive an image or
  container this run did not start.

## Driving conventions

- Drive the release binary (`target/release/schlange`), not `cargo run` of a debug build.
- Every command is literal; keep paths and flags unchanged. Paths are relative to the
  repository root.
- Each `sim run` starts from an empty simulated forge; scenarios do not share state.
- Prefer `--json` when asserting; the text output is for humans and may change wording.

## Proof and skip reporting

- CLI proof is the command, its stdout and stderr, and its exit code, captured by `verify.sh`
  into `evidence/<run>/<step>.txt` with a PASS/FAIL line in `proof.md`.
- Scenario proof is the event log (events and decisions with virtual time), the expectations
  and the invariant report. `not_checked` invariants are reported as such, never as passed.
- Record the feature ID with every run (`--feature <id>`).
- A feature whose `Driving it` section says **Not drivable yet** is reported as unreachable
  with that reason; do not report it as verified through another feature's scenario.

## Feature entry contract

Each feature file starts with YAML frontmatter, then an H1 title and one paragraph on the
behaviour in our own words. It then has exactly four H2 sections in this order:

1. `Sub-features`: short IDs, one line per behaviour.
2. `How to get to it (user POV)`: every entry point a user (or agent) has.
3. `Driving it with schlange`: starts with `Preconditions:`, then labeled bullets that pair
   each action with an exact command and the observable result.
4. `Gotchas`: traps that can waste or invalidate a verification run.

Frontmatter: `id` (= file name), `title`, `priority` (P1 = used by Arztagent or in effect as a
default, P2 = rest of merge queue and workflow, P3 = CI Insights, Test Engine, Stacks,
Dashboard), `arztagent` (bool), `status` (`missing` | `partial` | `conformant`), `inventory`,
`unsupported` (optional), `problems` (`MQ-…`, `W-…`), `source` (documentation page).
`conformant` needs green evidence and the critic's verdict (`AGENTS.md`).

`status` and `unsupported` feed the support matrix of `schlange config validate` (stage 5),
which decides per inventory entry the configuration uses (an option, action, attribute, enum
value, or a default that takes effect):

- feature `missing`: every entry of the feature is unsupported;
- feature `partial`: an entry is unsupported when it matches a pattern in the feature's
  `unsupported` list (same syntax as `inventory`, `*` matches any text), supported otherwise.
  List there every option, attribute, enum value or default of the feature that is not built,
  so that `config validate --strict` exits 2 for it. Leave out what is built, and say in the
  `Sub-features` section why a not-built item is not listed (for example because a stage 4
  error or another feature already flags every valid use of it);
- feature `conformant`: every entry is supported; `unsupported` must be empty.

The report names the reason per entry (`feature not built` or `not built in this partial
feature`). A default counts as used where its parent exists in the configuration (some list
element lacks the key) and no `defaults` section sets the option instead; `merge_queue` and
`commands_restrictions` exist even when not written.

## How the map is built

- [`_inventory.json`](_inventory.json) is generated by `cargo run -p inventory` from the pinned
  Mergify sources (`tools/mergify-sources.lock`); the entry counts are in its `counts` field.
  It holds identifiers, types and defaults only (null defaults of options included, since
  "none" is behaviour too); prose defaults are replaced by a hash (clean room).
- Every entry belongs to exactly one feature file through the frontmatter list `inventory`
  (IDs or patterns with `*`). The coverage test (`cargo test -p schlange-config --test
  coverage`) fails otherwise, and also when a problem ID does not exist, a P1 file names no
  `MQ-` case, or a file lacks one of the four sections. Every `unsupported` pattern must match
  an inventory entry that belongs to the same feature, and only `partial` features may have one.
- Features `S-…` are Schlange's own (KONZEPT.md, section 8) and have no inventory entries.

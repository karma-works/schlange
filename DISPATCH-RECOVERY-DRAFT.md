# Workflow dispatch recovery draft (experimental)

A crash after the engine checkpoint and before the existing intent can lose a dispatch. The simulator regression `dispatch-before-intent-crash.yaml` exercises that boundary; a second case prevents replay after send. Neither test is verified until run.

Use a versioned, durable outbox entry for each side-effect decision, with a unique session/operation identity and status `prepared` or `may_have_sent`. Insert all step entries and the resulting state in one SQLite transaction guarded by the current holder. The recovery read uses one SQLite snapshot. Before attempting a POST, atomically transition its entry to `may_have_sent` with the holder fence. Never automatically resend such an entry: a crash after transition can mean zero or one remote dispatch. Persist and report the uncertainty until explicitly resolved. Any old-format pending work is unknown, not prepared.

A prepared dispatch requires a fresh repository identity view, rules/config and security state, plus an ingress/lease fence. Capture the original triggering rule/config, PR head and base, target workflow/ref, rendered inputs, event and any actor/permission proof with the entry; current `Op::Dispatch` does not carry this evidence. Revalidate the actual triggering condition and original intent, preserving the original fired key on cancellation. If evidence is missing or stale, retain a durable cancellation/uncertainty reason instead of executing. Multiple dispatches from one rule have separate entries. Ref resolution must be explicit and revalidated; do not silently substitute a changed default branch.

The response's application, intent resolution, new checkpoint and all successor decisions must be transactional. Empty/delayed forge replies are not acknowledgements. A session/operation nonce distinguishes delayed replies and pre-upgrade state; legacy pending work is held. A schema/protocol gate must reject older writers, including a process using the same holder ID. None of these requirements provides atomicity with GitHub: lease loss or remote changes between final fence and HTTP remains a bounded residual, and no safe mechanism guarantees exactly-once dispatch.

Tests needed: crash before/after checkpoint, before/after prepared→may-have-sent, during HTTP, after 2xx before reply commit, and at each multi-action boundary; duplicate/stale replies, changed rule/head/base/ref, lease/ingress changes, takeover, migration/downgrade, missing/denied reads, malformed data and uncertain outcome visibility. Verify client 401, 307/308, 429, transport and 5xx behavior on a fake, including server-committed response loss. The design is not implemented or independently verified.

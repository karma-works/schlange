## Main experimental changes

- `crates/schlange-core`: required Actions check grouping differs from non-required latest-suite behavior; typed app-qualified requirements, identity-unavailable holds, deferred responses/comments and checkpoint-only identity batch publication were prototyped. Holds are additive. This is not a general crash recovery protocol, and batch completeness depends on the caller.
- `crates/schlange-github/src/{api,client,forge,service}.rs` and fake: experimental stricter suite/status/requirement reads, two-pass candidate reads, process-local ingress epoch and scoped write gate, startup holds, and conservative fail-stop on changed ingress/deferred effects. Reads are not atomic on GitHub; commands/checkboxes and missing or delayed webhooks remain unresolved. Required Actions workflow/job identity is not fully implemented. No general durable inbox exists here.
- `crates/schlange-github/src/api.rs` and `client.rs`: an experimental non-clone ref-created receipt and single-write send path avoid retries, 401 reattempts and redirect following; a successful response alone does not establish artifact ownership or authorization. It is not bound to a service session and is not used for recovery.
- `crates/schlange-github/src/store.rs`: experimental `build_claims` stores exact decision/checkpoint and a claim, rejects additional pending intents, checks SQLite holder and expiry under an immediate transaction, blocks journal checkpoint/intent/done while claimed, and fails legacy `recover()` closed if any claim exists. SQLite triggers also block direct checkpoint/intent SQL while a claim exists. Those triggers protect rows only: they do not fence already-running old workers, in-flight remote requests, other state tables, malicious DDL or remote ABA. A caller supplies session, ingress epoch and remote-fence strings; none is authenticated. No claim proves that a partial build can be replayed or safely discarded.
- `store.rs` also contains `#[cfg(test)]`-only `prepare_build_step` and `prepare_engine_build_step`: prototypes for atomic checkpoint plus one BuildCar intent, seeded session/revision CAS, a separate seeded sequence high-water, and deriving the complete decision list from the persisted predecessor and core event. The latter returns all decisions only after commit, checks affected rows, and rejects a changed predecessor. Its session and table are test-only; comparing serialized state cannot detect ABA. It does not implement actual session issuance, history/sequence migration, durable timers, reply-and-intent completion, old-writer exclusion, or service integration. Do not call it production recovery.
- The isolated lease file contains earlier partial metadata error/mismatch hardening, not a proof of safe lineage. The parent separately investigated transactional lease ownership in main; review main independently rather than copying the slice wholesale.

## Safety blockers and next steps

1. Define a real fenced per-process session and monotonic revision/operation identity, with safe legacy migration and an explicit cooperating-writer boundary. Legacy `max_seq` sees unresolved intents only; completed sequence history cannot be reconstructed. Existing old workers can have read prior state and can still send network requests even if database triggers later block their writes. Unknown lineage and ambiguous operations must remain held.
2. Replace the actual worker's checkpoint-before-intent and done-before-reply crash windows on the narrow BuildCar path with atomic, revision-bound transactions. Preserve the full engine output, timer obligations, state, all side effects and ambiguous outcomes; return no successful completion when a write is ignored or a transaction fails. Do not weaken I0–I5 or make cosmetics gate landing.
3. Bind each network attempt to an exact durable claim, live service session, repo, holder, ingress and fresh lease/fence. Validate exact request and authenticated response, enforce one-shot behavior, and commit the verified result and claim/intent completion atomically. A remote lease read and GitHub write cannot be atomic. No-op, timeouts, 5xx, partial builds, process crashes and stale or forged artifacts require conservative unknown handling; never infer ownership from branch name or blindly retry/delete.
4. Finish the actual held-service 403/restart/recovery scenario with deterministic fake HTTP barriers, signed ingress and lease races, fault clear, exact journal and request assertions, then prove a safe merge. Keep uncertain commands/checkbox provenance held; process-local epochs are not a durable inbox.
5. Obtain independent critic review and the repository's verification evidence before promotion. The latest critic also noted any session-marker trigger scheme must protect all state-bearing legacy writes and support atomic marker-aware commits; such triggers alone cannot exclude old network activity.

This branch is an experimental handoff, not a deployment. There is no claim that the feature is conformant or ready for Arztagent production.
